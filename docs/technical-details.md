# Технические нюансы Infiniti QX50 J55 Monitoring

![Infiniti QX50 J55 Monitoring](preview.png)

Бортовой монитор на ESP32 с TFT-дисплеем и веб-интерфейсом настройки.
Считывает параметры автомобиля через диагностический протокол UDS (ISO 14229) по шине CAN (OBD-II).
При выходе параметров за пределы нормы — воспроизводит звуковой сигнал через бузер и показывает оверлей на дисплее.

В версии прошивки XXXX.Y.Z каждое число означает следующее:
1. XXXX — год выпуска релиза прошивки.
2. Y — мажорная версия (Major). Указывает на крупные изменения, новые функции или глобальное обновление архитектуры.
3. Z — минорная версия (Minor). Указывает на мелкие доработки, исправления ошибок или добавление небольших возможностей в рамках текущего мажора.

Версия задается в одном месте — `FW_VERSION` в [include/Version.h](../include/Version.h). Оттуда она
попадает на дисплей, в `GET /version` и `GET /metrics`, и с ней же CI сверяет имя тега при релизе.

## 1. Подключение оборудования

### TFT-дисплей (ST7789, 240×240) — только для ESP32 DEVKIT1

| Дисплей | ESP32 GPIO | Описание |
|---------|-----------|----------|
| SDA / MOSI | GPIO **23** | Данные SPI |
| SCL / SCLK | GPIO **18** | Тактирование SPI |
| RES / RST  | GPIO **4**  | Сброс дисплея |
| DC / RS    | GPIO **15** | Данные / команда |
| BLK        | GPIO **27** через 500 Ом | Управление яркостью, если вывод есть |
| CS         | —           | Не подключать (CS=-1, дисплей всегда выбран) |
| VCC        | **3.3 В**   | Питание |
| GND        | **GND**     | Земля |

> Дисплей работает на 3.3 В. Не подключайте к 5 В — это выведет его из строя.
>
> Вывод BLK необязателен. Одна и та же прошивка работает с дисплеями без BLK и с дисплеями, у которых
> BLK подключен к GPIO 27. Во втором случае яркость регулируется через веб-интерфейс от 10 до 100%.
> Если BLK конкретного модуля напрямую питает светодиоды, а не является управляющим входом,
> используйте транзистор или MOSFET согласно документации модуля.

---

### Питание WT32-SC01 Plus

Преобразователь DC-DC понижает бортовое напряжение 12–14 В до 5 В. Выход `+5 В` подключается к
контакту 1 разъема `EXT_IO_1`, а выход `GND` — к контакту 2. Контакты считаются слева направо,
если смотреть на плату так же, как на схеме подключения.

Питание 3,3 В для WVCMCU-230 и цепи пассивного бузера берется с контакта 2 разъема `EXT_IO_2`,
второго слева. Земля CAN-трансивера и бузера подключается непосредственно к `GND` выхода DC-DC;
таким образом, все компоненты имеют общую землю.

---

### CAN-модуль WVCMCU-230 (SN65HVD230) — для обеих платформ

| Модуль | ESP32 DEVKIT1 | WT32-SC01 Plus | Описание |
|--------|----------------|----------------|----------|
| CTX    | GPIO **32** | GPIO **10**, `EXT_IO_1` контакт 3 слева | CAN TX (МК → трансивер) |
| CRX    | GPIO **34** | GPIO **11**, `EXT_IO_1` контакт 4 слева | CAN RX (трансивер → МК) |
| VCC    | **3,3 В** | **3,3 В**, `EXT_IO_2` контакт 2 слева | Питание |
| GND    | **GND** | `GND` выхода DC-DC | Общая земля |
| CANH   | OBD-II пин **6** | OBD-II пин **6** | Шина CAN High |
| CANL   | OBD-II пин **14** | OBD-II пин **14** | Шина CAN Low |

> На WT32-SC01 Plus GPIO 10 и GPIO 11 выведены на разъем `EXT_IO_1` и не конфликтуют со встроенными
> дисплеем и сенсорной панелью.

> ESP32 активно опрашивает блоки управления двигателем (ECM) и трансмиссией (TCM) по протоколу UDS, отправляя запросы `ReadDataByIdentifier` (сервис 0x22). Это безопасно: запросы стандартны, используются штатным дилерским оборудованием.

> Скорость шины: **500 кбит/с** (стандарт для большинства автомобилей, в т.ч. Infiniti QX50 J55).

---

### Пассивный бузер — для обеих платформ

| Бузер | ESP32 DEVKIT1 | WT32-SC01 Plus | Описание |
|-------|----------------|----------------|----------|
| Питание | **3,3 В** | **3,3 В**, `EXT_IO_2` контакт 2 слева | Питание бузера |
| Управление | GPIO **26** | GPIO **12**, `EXT_IO_1` контакт 5 слева | Через резистор 1 кОм и 2N5551 |
| GND | **GND** | `GND` выхода DC-DC | Общая земля |

При включении устройства бузер воспроизводит короткую мелодию приветствия (в стиле BIOS POST). При срабатывании алерта — сигнал оповещения.

> На WT32-SC01 Plus есть встроенный I2S-усилитель 2,5 Вт и выход `SPK+/SPK-`, но самого динамика
> на плате нет. Текущая прошивка этот выход не использует и воспроизводит сигналы внешним пассивным
> бузером на GPIO 12.

## 2. USB-устройство в WSL

ESP32 DEVKIT1 подключается через мост CP2102, CH340 или CH9102. WT32-SC01 Plus
использует встроенный USB Serial/JTAG. Передайте USB-устройство в WSL и проверьте
доступный Linux-порт:

```bash
ls -l /dev/ttyUSB* /dev/ttyACM* 2>/dev/null
```

Обычно DEVKIT1 появляется как `/dev/ttyUSB0`, а WT32 — как `/dev/ttyACM0`. Если
у текущего пользователя нет доступа к порту, добавьте его в группу `dialout`, затем
перезапустите сеанс WSL:

```bash
sudo usermod -aG dialout "$USER"
```

## 3. Первичная прошивка из WSL через esptool

Команды этого раздела выполняет только владелец устройства. Для ESP32 DEVKIT1 нужны
`bootloader.bin`, `partitions.bin` и `firmware.bin`:

```bash
python3 -m esptool --chip esp32 --port /dev/ttyUSB0 --baud 921600 erase_flash
python3 -m esptool --chip esp32 --port /dev/ttyUSB0 --baud 921600 \
  write_flash --flash_mode dio --flash_freq 40m \
  0x1000 bootloader.bin 0x8000 partitions.bin 0x10000 firmware.bin
```

Для WT32-SC01 Plus нужны `bootloader_s3.bin`, `partitions_s3.bin` и
`firmware_s3.bin`. Загрузчик от ESP32 DEVKIT1 использовать нельзя:

```bash
python3 -m esptool --chip esp32s3 --port /dev/ttyACM0 --baud 460800 erase_flash
python3 -m esptool --chip esp32s3 --port /dev/ttyACM0 --baud 460800 \
  write_flash --flash_mode qio --flash_freq 80m --flash_size 16MB \
  0x0000 bootloader_s3.bin 0x8000 partitions_s3.bin 0x10000 firmware_s3.bin
```

Для входа WT32 в загрузчик подключите плату по USB-C, зажмите `BOOT`, нажмите и
отпустите `RESET`, затем отпустите `BOOT`. После прошивки нажмите `RESET`.

## 4. Мониторинг UART из WSL

Подключите терминал PlatformIO к тому же Linux-порту со скоростью 115200 бод:

```bash
platformio device monitor --port /dev/ttyUSB0 --baud 115200
```

Для WT32 обычно нужно заменить порт на `/dev/ttyACM0`. После нажатия `EN` или
`RESET` в терминале появится журнал загрузки, состояние CAN-шины, ответы UDS,
значения датчиков и срабатывания алертов.

> Если в окне нет вывода — проверьте правильность порта COM и скорость 115200. Порт должен совпадать с тем, что отображается в Диспетчере устройств (**Silicon Labs CP210x**).

> **Предупреждения при старте — это нормально.** При каждом включении ESP32 ROM-загрузчик выводит несколько служебных строк на скорости 74880 бод (не 115200), поэтому терминал может показать их как мусор: `RX FRAMING ERROR`, `invalid UTF-8 byte sequence`, `No core dump partition found`. Эти сообщения не относятся к нашему коду и не влияют на работу устройства — просто игнорируйте их.

## 5. Подключение к WiFi и веб-интерфейс

ESP32 создаёт собственную точку доступа (Access Point) — интернет не нужен.

| Параметр | Значение по умолчанию |
|----------|-----------------------|
| Сеть     | `QX50Monitoring`      |
| Пароль   | `infiniti`            |
| Адрес    | http://192.168.4.1    |

> Имя сети и пароль можно изменить через веб-интерфейс (раздел **«1. Настройка WiFi»**).
> После сохранения устройство перезагрузится с новыми настройками.

**Шаги:**

1. На телефоне или ноутбуке откройте список WiFi-сетей.
2. Подключитесь к сети **QX50Monitoring**, пароль `infiniti`.
3. Откройте браузер и перейдите по адресу **http://192.168.4.1**.
4. Откроется страница редактора конфигурации.
5. Можно забыть WiFi-сеть, чтобы телефон не подключался автоматически.

> **Мобильный интернет на телефоне продолжает работать.** Устройство намеренно не отдает
> по DHCP адрес шлюза, поэтому телефон не делает нашу сеть основной: запросы на `192.168.4.1`
> идут по WiFi, все остальные — по мобильной сети. Android при подключении спросит «Сеть не имеет
> доступа к интернету. Остаться подключенным?» — ответьте **«Да»**.
>
> Передачу данных **отключать не нужно** — без нее не работает проверка обновлений (глава 6).
> Отключить ее имеет смысл только если конкретный телефон все равно упорно теряет интернет:
> веб-интерфейс и OTA от этого работать не перестанут.

### HTTP API

| Метод | Путь | Описание |
|-------|------|---------|
| `GET`  | `/`               | Главная страница (HTML) — редактор конфигурации |
| `GET`  | `/live`           | Страница онлайн мониторинга (HTML) — метрики в реальном времени |
| `GET`  | `/health`         | Страница работоспособности устройства (HTML) |
| `GET`  | `/metrics`        | Текущие значения метрик и их состояния (JSON, включая `version`) |
| `GET`  | `/reset-history`  | История причин последних загрузок устройства (JSON) |
| `GET`  | `/version`        | Версия прошивки, метка сборки, слот OTA, окружение, аптайм (JSON) |
| `GET`  | `/config`         | Текущий конфиг порогов (JSON) |
| `POST` | `/config`         | Сохранить конфиг порогов (JSON body) |
| `POST` | `/reset`          | Сбросить конфиг порогов к заводским значениям |
| `GET`  | `/wifi`           | Текущие WiFi-настройки (JSON: ssid, password) |
| `POST` | `/wifi`           | Сохранить WiFi-настройки (JSON body) |
| `POST` | `/restart`        | Перезагрузить устройство |
| `GET`  | `/alerts`         | Журнал сработавших алертов (JSON) |
| `POST` | `/alerts-clear`   | Очистить журнал алертов |
| `GET`  | `/checks`         | Конфиг проверок алертов (JSON) |
| `POST` | `/checks`         | Сохранить конфиг проверок (JSON body) |
| `GET`  | `/update`         | Страница OTA-обновления прошивки (редирект на `/`) |
| `POST` | `/update`         | Загрузить `.bin` файл прошивки (multipart) |
| `GET`  | `/slots`          | Что записано в обоих слотах OTA (JSON) |
| `POST` | `/boot-slot`      | Сделать слот загрузочным (`?slot=ota_0` или `?slot=ota_1`) |

Ответ `GET /version`:

```json
{
  "version": "2026.3.1",
  "build": "Jul 27 2026 14:02:11",
  "slot": "ota_0",
  "env": "esp32",
  "uptime_s": 12345
}
```

`slot` — раздел, из которого загрузилась работающая прошивка (`ota_0` или `ota_1`),
`env` — окружение сборки (`esp32`, `esp32-mock`, `esp32s3-wt32`, `esp32s3-wt32-mock`).

Ответ `GET /slots`:

```json
{
  "slots": [
    {
      "label": "ota_0", "valid": true, "running": true, "boot": true,
      "version": "2026.3.3", "env": "esp32", "build": "Aug  6 2026 01:15:19",
      "size": 1835008, "used": 1080325
    },
    {
      "label": "ota_1", "valid": true, "running": false, "boot": false,
      "version": "2026.3.2", "env": "esp32", "build": "Aug  3 2026 04:49:07",
      "size": 1835008, "used": 1076032
    }
  ]
}
```

`valid` — в слоте лежит образ приложения, `running` — из него работает прошивка сейчас,
`boot` — с него устройство загрузится после перезагрузки, `used` — длина образа в байтах.
Пустые `version`, `env` и `build` означают, что в образе нет маркера версии (прошивка старее
этой возможности) — см. главу 6.

### Онлайн мониторинг (веб)

Страница **http://192.168.4.1/live** (ссылка **«📊 Онлайн мониторинг →»** на главной)
показывает все метрики в реальном времени прямо в браузере — удобно, когда дисплей не виден.

- **Сетка метрик** — 9 карточек по 3 в ряд, в том же порядке, что и на дисплее:
  RAD-ANT · ENG-ANT · ENG-OIL / ENG-RPM · OIL-PR-V · TURBO-V / BATTERY-V · RPM-POLL · CVT-FLD.
  Значения обновляются каждые **0.5 сек** (опрос `/metrics`), цвет левой полосы и числа
  отражает состояние (синий / зелёный / жёлтый / красный / серый «нет данных»).
- **Индикатор связи** — строка «В сети · v2026.3.1 · обновлено ЧЧ:ММ:СС · аптайм …» либо
  «Нет связи с устройством». Версия прошивки приходит в том же ответе `/metrics`.
- **Баннер ошибок** — красная плашка «⚠ Зафиксированы ошибки…» появляется, если в журнале
  есть срабатывания, и исчезает после его очистки.
- **История срабатываний** — та же таблица журнала алертов, что и на главной, с кнопкой
  **«🗑 Очистить историю»**. Обновляется каждые **5 сек** и сразу после очистки.

## 6. OTA — обновление прошивки по воздуху

После первой прошивки через USB все последующие обновления можно загружать **без кабеля** прямо через браузер.

### Что нужно

- Файл `firmware.bin` новой версии (из релиза или собранный PlatformIO: `.pio/build/esp32/firmware.bin`).
- Подключение к точке доступа **QX50Monitoring**.

### Порядок обновления

1. Подключитесь к WiFi-сети **QX50Monitoring** (пароль `infiniti`).
2. Откройте **http://192.168.4.1** в браузере.
3. Прокрутите страницу вниз до раздела **«↑ OTA — Обновление прошивки»**.
4. Нажмите **«Выбрать .bin»** и укажите файл `firmware.bin`.
5. Нажмите **«↑ Загрузить»** и подтвердите в диалоге.
6. Дождитесь заполнения прогресс-бара и сообщения **«✓ Прошивка записана. Перезагрузка...»**.
7. ESP32 автоматически перезагрузится с новой прошивкой (~2–3 секунды).

> **Страница перестанет отвечать** на время перезагрузки — это нормально. Через 5–10 секунд обновите страницу браузера.

> **Первичная прошивка через USB обязательна.** OTA-обновления возможны только после того, как устройство хотя бы один раз прошито через USB с помощью `esptool` или PlatformIO.

### Проверка обновлений

В том же разделе **«↑ 6. Обновление прошивки»**, над формой загрузки `.bin`, лежит карточка
**«↻ Проверка обновлений»**: текущая версия прошивки, метка сборки со слотом OTA и кнопка
**«↻ Проверить обновления»**.

Устройство в интернет не выходит, поэтому релизы спрашивает **браузер телефона**: запрос
на `192.168.4.1` идет по WiFi, запрос к `api.github.com` — по мобильной сети.

**Автопроверка при открытии страницы.** Главная страница проверяет релизы сама, в фоне —
загрузку и работу интерфейса это не задерживает, а при отсутствии интернета просто ничего
не происходит. Если на GitHub версия новее, поверх страницы появляется окно **«↑ Доступна
новая прошивка»** с кнопками **«Перейти к обновлению»** (открывает и прокручивает к разделу 5)
и **«Позже»**; окно закрывается также кликом по затемнению или клавишей Esc.

Проверка идет не чаще **одного раза в 5 минут**: время последней попытки лежит
в `localStorage` браузера, поэтому перезагрузка страницы, закрытие вкладки и перезапуск
браузера отсчет не сбрасывают — иначе несколько открытий страницы подряд быстро упирались бы
в лимит GitHub. Кнопка **«↻ Проверить обновления»** этот интервал игнорирует и работает всегда.

**Что нужно от телефона:**

- включенная передача данных (мобильный интернет);
- разрешение остаться в сети без интернета — на вопрос Android «Сеть не имеет доступа
  к интернету. Остаться подключенным?» ответьте **«Да»**.

**Что показывает кнопка:**

| Ситуация | Сообщение |
|----------|-----------|
| Есть версия новее | «Доступна версия X (у вас Y)» + описание релиза и ссылки на релиз и `firmware.bin` |
| Установлена актуальная | «✓ Установлена последняя версия X» |
| Релизов нет | «Релизы еще не опубликованы» |
| Слишком частые проверки | «Превышен лимит запросов к GitHub, попробуйте позже» — без авторизации GitHub отдает 60 запросов в час на один адрес |
| Нет интернета у телефона | «Нет доступа к интернету» + напоминание включить мобильные данные |

Запрос обрывается через **5 секунд**: в сети без интернета DNS не отвечает, и ждать дольше
нечего. Ссылка **«Все релизы»** под карточкой ведет на страницу релизов напрямую и работает,
даже если проверка не прошла.

Если релиз новее, в карточке появляется кнопка **«↓ Скачать и установить»**: браузер сам скачивает
OTA-образ для подключенной платы и сразу отдает его в прошивку, прогресс идет в полосе формы ниже.

Файл берется не из ассетов релиза, а из служебной ветки `firmware`. WEB UI выбирает его
по окружению сборки устройства:

```
https://raw.githubusercontent.com/oSkrobuk/infiniti-qx50-j55-monitoring/firmware/<версия>/firmware.bin
https://raw.githubusercontent.com/oSkrobuk/infiniti-qx50-j55-monitoring/firmware/<версия>/firmware_s3.bin
```

Ассеты релизов GitHub отдает с хоста `release-assets.githubusercontent.com` **без заголовка
`Access-Control-Allow-Origin`**, и браузер не пускает такой ответ в скрипт — запрос падает
еще до чтения файла (Safari сообщает об этом первым, но так ведут себя все браузеры).
У `raw.githubusercontent.com` заголовок есть, поэтому CI на каждом теге кладет прошивку
еще и в ветку `firmware`, в папку с номером версии. Версия в пути означает, что на
устройство не может приехать `.bin` от другого релиза.

Если скачать не удалось (сборки этой версии в ветке еще нет, оборвалась сеть), в карточке
появляется подсказка с причиной — скачайте `.bin` вручную по ссылке и залейте формой
**«↑ OTA — Загрузка .bin»**. Ручной способ работает всегда: обычное скачивание по ссылке
идет средствами браузера, и CORS ему не нужен.

Для ESP32 DEVKIT1 скачивается `firmware.bin`, для WT32-SC01 Plus — `firmware_s3.bin`.

### Проверка совместимости OTA-образа

Автоматическая и ручная OTA-загрузка проходят одинаковую проверку на самом устройстве. Во время
приема файла прошивка ищет встроенный маркер `QX50-FW-TAG`, читает из него окружение сборки и до
активации нового слота сравнивает его с работающей платой.

Совместимыми считаются real- и mock-сборки одной аппаратной платформы:

- `esp32` и `esp32-mock` — ESP32 DEVKIT1
- `esp32s3-wt32` и `esp32s3-wt32-mock` — WT32-SC01 Plus

Автоматическое обновление mock-сборки загружает опубликованный real-образ той же платы. После
обновления устройство продолжит работу уже без симуляции данных.

Образ WT32 нельзя установить на ESP32 DEVKIT1 и наоборот. Файл без маркера, в том числе старая
или сторонняя прошивка, также отклоняется. Проверка выполняется до `Update.end(true)`, поэтому
отклоненный образ не становится загрузочным, а устройство продолжает работать с текущего слота.

Ограничение относится только к OTA через веб-интерфейс. При необходимости старый образ без маркера
по-прежнему можно записать вручную через USB-инструменты.

### Слоты прошивки и откат

Под карточкой проверки обновлений лежит карточка **«⇆ Слоты прошивки»**: для каждого из двух
слотов (`ota_0` и `ota_1`) видно, что в нем записано — версия, окружение сборки, дата сборки
и размер образа, — а также метки **«работает сейчас»** и **«загрузится после перезагрузки»**.

Кнопка **«⇆ Загрузиться отсюда»** у неактивного слота переключает загрузку на лежащую там
прошивку: устройство меняет запись в `otadata` и перезагружается. Так возвращаются к предыдущей
версии, если новая чем-то не устроила — заново качать `.bin` не нужно, старый образ никуда
не делся. Настройки, журнал алертов и файловая система лежат в отдельном разделе `spiffs`,
поэтому переключение слота их не трогает.

> Версию соседнего слота устройство читает прямо из его образа: при сборке в прошивку
> вшивается маркер `QX50-FW-TAG:версия|окружение|дата сборки|`, и он ищется линейным чтением
> раздела (результат кешируется по хешу образа, так что повторные открытия карточки бесплатны).
> У прошивок, собранных до появления этой карточки, маркера нет — для них показывается
> «Версия неизвестна», хотя переключиться на такой слот все равно можно.

### Как устроено OTA (техническая справка)

Для плат используются разные таблицы разделов. ESP32 DEVKIT1 с 4 МБ флеша получает два
OTA-слота по 1,875 МБ и LittleFS на 192 КБ. WT32-SC01 Plus с 16 МБ получает два слота по
6,25 МБ, LittleFS на 3,375 МБ и раздел coredump на 64 КБ. Полный расчет, размеры текущих
бинарников и порядок перехода приведены в [описании разделов флеша](flash-layout.md).

При OTA-обновлении:
1. Новая прошивка записывается в **неактивный** слот.
2. `otadata` обновляется, указывая на новый слот.
3. ESP32 перезагружается и загружается из нового слота.

Старая прошивка остаётся в предыдущем слоте до следующего OTA-обновления, и на нее можно
вернуться карточкой **«⇆ Слоты прошивки»**.

### Файлы LittleFS

В разделе `spiffs` (LittleFS, 192 КБ на ESP32 и 3,375 МБ на WT32) хранятся четыре файла:

| Файл | Описание |
|------|---------|
| `/config.json` | Пороги метрик, параметры системы, яркость и настройки WiFi |
| `/checks.json` | Конфиг проверок алертов (тайминги + режим повтора + пороги) |
| `/alerts.json` | Журнал сработавших алертов (сохраняется между перезагрузками) |
| `/resets.json` | Причины последних десяти загрузок устройства |

## 7. Метрики на дисплее

Дисплей 240×240 разделён на три секции. Цвет каждого значения меняется плавно согласно настроенным порогам.

При срабатывании алерта дисплей переходит в **режим оверлея** — метрики скрываются и на весь экран отображается код и описание алерта (например, `E01 — Engine oil temperature exceeded maximum threshold`). Оверлей исчезает автоматически через **5 секунд**.

### TEMPERATURE — температурные датчики

| Метка | Описание | Единица |
|-------|----------|---------|
| **RAD-ANT** | Температура антифриза в радиаторе | °C |
| **ENG-ANT** | Температура антифриза ДВС | °C |
| **ENG-OIL** | Температура моторного масла ДВС | °C |

Цвет меняется по схеме **синий → зелёный → красный** (холодно → норма → перегрев).

### ENGINE — параметры двигателя

| Метка | Описание | Единица |
|-------|----------|---------|
| **ENG-RPM** | Обороты двигателя | об/мин |
| **OIL-PR-V** | Напряжение датчика давления масла ДВС | В |
| **TURBO-V** | Напряжение датчика давления наддува (турбина) | В |

### OTHER — прочие параметры

| Метка | Описание | Единица |
|-------|----------|---------|
| **BATTERY-V** | Напряжение бортовой сети | В |
| **RPM-POLL** | Период обновления оборотов — интервал между двумя UDS-запросами RPM | с |
| **CVT-FLD** | Температура масла вариатора (CVT) | °C |

> **RPM-POLL — это не время ответа ECU.** Значение показывает, как часто устройство успевает
> обновлять обороты: отдельная задача по кругу опрашивает 8 параметров с паузой `poll_interval_ms`,
> поэтому RPM-POLL ≈ `poll_interval_ms × 8` (при 30 мс — около 0.24 с).

### Цветовая индикация

| Цвет | Значение |
|------|----------|
| 🔵 Синий | Нет данных или агрегат не прогрет или не готов к работе |
| 🟢 Зелёный | Рабочий / нормальный диапазон |
| 🟡 Жёлтый | Переходная зона (плавный градиент) |
| 🔴 Красный | Выход за пределы нормы / перегрев |

## 8. Настройка порогов

Все пороги хранятся в файловой системе LittleFS (`/config.json`) и доступны для редактирования через веб-интерфейс.

Каждая карточка содержит кнопку **«↺ Сброс»** — сбрасывает поля только этой карточки к заводским значениям без сохранения. Кнопка **«↺ По умолчанию»** в разделе «Конфигурация метрик» сбрасывает весь конфиг и немедленно сохраняет его.

> При обновлении прошивки конфиг мигрирует по отдельным полям: известные пользовательские значения
> сохраняются, новые параметры получают актуальные значения по умолчанию, удаленные параметры
> отбрасываются. CRC32 блока defaults используется только для обнаружения необходимости миграции.

### 🌡️ Температурные датчики

Три порога: минимум (не прогрет), цель (рабочая температура), максимум (перегрев).

| Секция | Датчик | Мин, °C | Цель, °C | Макс, °C |
|--------|--------|---------|----------|---------|
| `oil` | ENG-OIL — моторное масло ДВС | 50 | 90 | 98 |
| `coolant` | ENG-ANT — антифриз ДВС | 50 | 90 | 93 |
| `radiator` | RAD-ANT — антифриз радиатора | 0 | 50 | 90 |
| `transmission` | CVT-FLD — масло вариатора | 50 | 80 | 98 |

### ⚙️ Обороты двигателя (ENG-RPM)

Секция `rpm` — три порога цветовых зон:

| Параметр | Знач. по умолч. | Описание |
|----------|----------------|---------|
| `green_start` | 1000 об/мин | Начало зелёной зоны |
| `green_end`   | 3500 об/мин | Конец зелёной зоны |
| `red_start`   | 4500 об/мин | Начало красной зоны |

Ниже `green_start` — синий, выше `red_start` — красный, между зонами — плавный переход через жёлтый.

### 🛢️ Датчик давления масла ДВС (OIL-PR-V)

Секция `oil_pressure` — минимально допустимое **напряжение датчика** зависит от оборотов:

| Параметр | Знач. по умолч. | Описание |
|----------|----------------|---------|
| `rpm_threshold` | 3000 об/мин | Граница низких / высоких оборотов |
| `min_low`       | 1.45 В | Минимум при RPM < threshold (красный ниже) |
| `min_high`      | 3.1 В  | Минимум при RPM ≥ threshold (красный ниже) |

### 💨 Наддув (TURBO-V)

Секция `boost` — цветовые пороги напряжения датчика MAP:

| Параметр | Знач. по умолч. | Описание |
|----------|----------------|---------|
| `blue_max`  | 1.30 В | ≤ этого — синий (нет давления) |
| `green_min` | 1.58 В | ≥ этого — зелёный (наддув есть) |

Между порогами — плавный переход синий → жёлтый → зелёный.

### 🔋 Бортовая сеть (BATTERY-V)

Секция `battery` — пороги напряжения в Вольтах:

| Параметр | Знач. по умолч. | Описание |
|----------|----------------|---------|
| `red_low`   | 11.5 В | Ниже — красный (разряд) |
| `green_min` | 12.0 В | Начало зелёной зоны |
| `green_max` | 14.6 В | Конец зелёной зоны |
| `red_high`  | 14.9 В | Выше — красный (перезаряд) |

### ⏱️ Период обновления RPM (RPM-POLL)

Секция `poll_time` — интервал между двумя последовательными UDS-запросами оборотов (секунды):

| Параметр | Знач. по умолч. | Описание |
|----------|----------------|---------|
| `green_max` | 0.20 с | ≤ этого — зелёный (обороты обновляются часто) |
| `red_min`   | 0.50 с | ≥ этого — красный (обороты обновляются слишком редко) |

### 🔧 Системные параметры UDS-опроса

Секция `system` — управляет планировщиком запросов:

| Параметр | Знач. по умолч. | Описание |
|----------|----------------|---------|
| `poll_interval_ms` | 30 мс  | Пауза между последовательными UDS-запросами |
| `stale_ms`         | 1000 мс | Через сколько мс без ответа значение обнуляется |

### 📶 WiFi точка доступа

Секция `wifi` — настройки AP (изменяются в разделе «1. Настройка WiFi»):

| Параметр | Знач. по умолч. | Описание |
|----------|----------------|---------|
| `ssid`     | `QX50Monitoring` | Имя WiFi-сети |
| `password` | `infiniti`       | Пароль WiFi-сети |

## 9. Система алертов

Устройство непрерывно отслеживает параметры и при выходе за пределы нормы:

1. Воспроизводит **звуковой сигнал** через внешний пассивный бузер.
2. Показывает **оверлей на дисплее** с кодом и описанием (5 секунд).
3. Записывает событие в **журнал алертов** (`/alerts.json`), который сохраняется между перезагрузками.

### Тайминги алертов

Два параметра, общих для всех девяти проверок. Задаются в секундах в разделе
**«⚠ 4. Конфигурация проверок»**, хранятся в `/checks.json` в миллисекундах:

| Параметр | Знач. по умолч. | Диапазон | Описание |
|----------|----------------|----------|---------|
| `confirm_ms` | 1000 мс (1 с) | 0…60 с | Сколько условие должно держаться, прежде чем поднимется алерт |
| `retrigger_ms` | 15000 мс (15 с) | 1…3600 с | Как часто напоминать о сохраняющейся неисправности (режим повтора) |

> **Показание, выскочившее за диапазон на доли секунды, алертом не считается**: ни сигнала,
> ни записи в журнале не будет. Как только значение возвращается в норму, отсчёт начинается
> заново — то же самое происходит, если по метрике перестают приходить кадры. Подтверждение
> в `0 с` отключает эту защиту: алерт срабатывает на первом же замере за порогом.

Каждая проверка имеет два режима, которые переключаются toggle-переключателем в Web UI:

| Режим | Поведение |
|-------|----------|
| **При постоянной ошибке повтор раз в N сек** (toggle вкл) | Пока условие нарушено — сигнал и оверлей повторяются каждые `retrigger_ms` |
| **Однократно, пока код в журнале** (toggle выкл) | Сигнал срабатывает один раз и больше не повторяется, пока код остаётся в журнале алертов |

> **Toggle не отключает проверку.** Он переключает только режим оповещения: в обоих положениях
> условие продолжает проверяться, срабатывание пишется в журнал и показывается на дисплее.
> Полностью отключить проверку через веб-интерфейс нельзя.

> **Признак «уже показывали» — это запись в журнале, а не флаг сессии.** Как только код
> стёрт кнопкой «Очистить журнал», однократная проверка при сохраняющейся неисправности
> сработает заново — ждать перезагрузки устройства не нужно. И наоборот: перезагрузка МК
> сама по себе алерт не возвращает, потому что журнал переживает выключение питания.

### Коды алертов

| Код | Название | Описание | Параметры по умолч. |
|-----|---------|---------|-------------------|
| **E01** | Engine Oil Temp High | Температура масла ДВС превысила максимум | Max: 98 °C |
| **E02** | Engine Coolant Temp High | Температура ОЖ ДВС превысила максимум | Max: 96 °C |
| **E03** | Radiator Coolant Temp High | Температура ОЖ радиатора превысила максимум | Max: 90 °C |
| **E04** | CVT Oil Temp High | Температура масла вариатора превысила максимум | Max: 100 °C |
| **E05** | Engine RPM Overspeed | Обороты двигателя превысили максимум | Max: 6500 об/мин |
| **E06** | Battery Voltage Low | Напряжение бортовой сети упало ниже минимума | Min: 11.5 В |
| **E07** | Battery Voltage High | Напряжение бортовой сети превысило максимум | Max: 15.0 В |
| **E08** | Oil Pressure Low | Напряжение датчика давления масла ниже нормы для текущих оборотов | RPM порог: 3000, Min low: 1.4 В, Min high: 2.9 В |
| **E09** | Oil-Coolant Temp Delta High | Разница температур масла и антифриза ДВС превысила порог | Max дельта: 14 °C |

### Управление алертами через веб-интерфейс

На главной странице `http://192.168.4.1` доступны два раздела:

**Журнал алертов** — список всех сработавших проверок с количеством срабатываний.
Кнопка **«Очистить журнал»** удаляет все записи и файл `/alerts.json`, а заодно снимает
запрет на повторное срабатывание: после очистки алерт поднимется снова в любом режиме.

**Настройка проверок** — карточка **«⏱ Тайминги алертов»** задаёт подтверждение и интервал
повтора сразу для всех проверок, а для каждой проверки (E01–E09) можно:
- Переключить режим срабатывания (toggle): **«При постоянной ошибке повтор раз в N сек»** или **«Однократно, пока код в журнале»**.
- Изменить пороговые значения (одно или несколько в зависимости от проверки).
- Нажать **«↺ Сброс»** на карточке, чтобы восстановить заводские параметры только этой проверки.

Изменения сохраняются в `/checks.json` и применяются немедленно без перезагрузки.

## 10. UDS-опрос (техническая справка)

Устройство активно опрашивает два блока управления автомобиля по протоколу **UDS (ISO 14229)** через шину CAN.

| Блок | CAN ID | Описание |
|------|--------|---------|
| ECM  | `0x7E0` | Блок управления двигателем |
| TCM  | `0x7E1` | Блок управления трансмиссией (вариатором) |

### Список опрашиваемых параметров

| Блок | DID | Описание |
|------|-----|---------|
| ECM | `0x1201` | Обороты двигателя |
| ECM | `0x110E` | Давление наддува (турбина) |
| ECM | `0x1278` | Давление масла ДВС |
| ECM | `0x1103` | Напряжение бортовой сети |
| ECM | `0x1101` | Температура антифриза ДВС |
| ECM | `0x111F` | Температура моторного масла ДВС |
| ECM | `0x116B` | Температура антифриза радиатора |
| TCM | `0x110C` | Температура масла вариатора |

### Порядок работы планировщика

1. При старте — открывается расширенная диагностическая сессия (`0x10 0xC0`) на ECM, TCM и блоке света.
2. Отдельная задача с повышенным приоритетом каждые **30 мс** (настраивается) по кругу отправляет один
   `ReadDataByIdentifier` запрос (сервис `0x22`), независимо от отрисовки дисплея.
3. Каждые **2 секунды** — отправляется `Tester Present` (`0x3E 0x80`, без запроса ответа) на три блока
   для удержания сессии.
4. При отсутствии ответа более **1 секунды** (настраивается) значение обнуляется на дисплее.

## 11. Сборка из исходников (PlatformIO)

Проект собирается в WSL с помощью [PlatformIO](https://platformio.org/).

### Окружения сборки

| Окружение | Платформа | Данные | Команда сборки |
|-----------|-----------|--------|---------------|
| `esp32` | ESP32 DEVKIT1, ST7789 | Реальный CAN | `platformio run -e esp32` |
| `esp32-mock` | ESP32 DEVKIT1, ST7789 | Имитация | `platformio run -e esp32-mock` |
| `esp32s3-wt32` | WT32-SC01 Plus, ST7796 | Реальный CAN | `platformio run -e esp32s3-wt32` |
| `esp32s3-wt32-mock` | WT32-SC01 Plus, ST7796 | Имитация | `platformio run -e esp32s3-wt32-mock` |

### Прошивка ESP32 DEVKIT1

```
platformio run -e esp32 --target upload
```

Готовый бинарник для OTA или Flash Tool:
```
.pio/build/esp32/firmware.bin
```

### Прошивка WT32-SC01 Plus (ESP32-S3)

WT32-SC01 Plus **не имеет отдельного USB-UART чипа** (CP210x / CH340). Прошивка выполняется
через встроенный USB Serial/JTAG интерфейс ESP32-S3.

**Первая прошивка — вход в режим загрузки вручную:**

1. Подключите плату к компьютеру по USB-C.
2. Зажмите кнопку **BOOT** на плате.
3. Нажмите и отпустите кнопку **RESET**.
4. Отпустите **BOOT** — плата перейдёт в режим загрузки.
5. Выполните команду:

```
platformio run -e esp32s3-wt32 --target upload
```

**Последующие прошивки** через OTA работают стандартно — кнопки не нужны.

Готовый локальный бинарник:
```
.pio/build/esp32s3-wt32/firmware.bin
```

В черновик GitHub Release WT32 добавляется комплект `bootloader_s3.bin`, `partitions_s3.bin` и
`firmware_s3.bin`. Файлы без постфикса `_s3` в релизе предназначены только для ESP32 DEVKIT1.

### Юнит-тесты

Логика, не зависящая от железа (декодер CAN, конфиг, алерты, цветовые зоны, разбор образа
прошивки), собирается под хост обычным gcc и проверяется за секунды — ни платы, ни тулчейна
xtensa для этого не нужно. В корне лежит скрипт, который сам находит PlatformIO и компилятор:

```bash
./run-tests.sh                     # все наборы
./run-tests.sh -f test_ota_image   # один набор
./run-tests.sh -vvv                # подробный вывод
```

Все, что скрипт получает, он передает в `platformio test -e native` — то же самое можно вызвать
и напрямую, если оба инструмента есть в `PATH`. Эти же тесты CI прогоняет первым шагом:
пока они не прошли, ни одна прошивка не собирается.
