## Аварийная загрузка WT32 после переключения OTA-слота

### Наблюдение

- Пользователь изменял настройки через веб-интерфейс и, вероятно, переключил OTA-слот
- После этого WT32 циклически показывает экран с прочерками примерно на полсекунды,
  гаснет примерно на полсекунды и повторяет загрузку
- Прочерки ожидаемы сразу после старта, пока данные CAN еще не получены; повторная
  отрисовка всего экрана указывает на перезапуск устройства
- Устройство первоначально прошивал владелец; пользователь прошивку не загружал
- Неизвестно, выполнялся ли `erase_flash` при переходе на актуальную разметку
- В выбранном слоте могла остаться прошивка, созданная до изменения таблицы разделов

### История разметки flash

В коммите `9ef176c` (`Split flash layouts by board capacity`, 2026-09-02)
общая 4-МБ разметка была заменена отдельной 16-МБ разметкой WT32.

Старая общая разметка:

| Раздел | Адрес | Размер |
|---|---:|---:|
| `ota_0` | `0x10000` | `0x1C0000` |
| `ota_1` | `0x1D0000` | `0x1C0000` |
| `spiffs` / LittleFS | `0x390000` | `0x70000` |

Текущая разметка WT32:

| Раздел | Адрес | Размер |
|---|---:|---:|
| `ota_0` | `0x10000` | `0x640000` |
| `ota_1` | `0x650000` | `0x640000` |
| `spiffs` / LittleFS | `0xC90000` | `0x360000` |
| `coredump` | `0xFF0000` | `0x10000` |

Старый адрес `ota_1` (`0x1D0000`) после установки новой таблицы находится внутри
нового `ota_0` и больше не является отдельным загрузочным слотом. OTA обновляет
только приложение и не обновляет таблицу разделов по адресу `0x8000`.

### Предварительные выводы

- Если `partitions_s3.bin` после коммита `9ef176c` не записывался через USB,
  устройство продолжает использовать старую таблицу и изменение адресов не может
  быть непосредственной причиной текущего цикла
- Если новая таблица записывалась без полной очистки flash, в памяти могли остаться
  образы и данные от старой разметки; их физические адреса уже имеют другой смысл
- Перемещение LittleFS само по себе не должно вызывать цикл: прошивки используют
  `LittleFS.begin()` без жестко заданного адреса и находят раздел по текущей таблице
- При пустой новой LittleFS ожидается форматирование и создание настроек по умолчанию,
  а не перезагрузка; старые настройки и журналы при этом становятся недоступны
- Формально валидная старая прошивка может успешно начать загрузку, показать экран,
  а затем падать уже при инициализации WiFi, CAN, задач или другой логики
- Просадка питания остается возможной, но связь начала проблемы с переключением
  слота делает старую или поврежденную прошивку более вероятной причиной

## Витрина стандартных OBD-II PID

### Цель

Добавить сбор поддерживаемых автомобилем стандартных OBD-II Mode 01 PID для
отдельной витрины диагностических данных. Новый сбор не должен ухудшать период,
задержки или надежность основного UDS-опроса Infiniti DID.

### Приоритеты опроса

1. Основной UDS-опрос известных Infiniti DID имеет безусловный приоритет.
2. Выбранные стандартные OBD-II PID опрашиваются по одному запросу в секунду.
3. В начале каждой итерации `loop()` сначала проверяется и выполняется основной
   UDS-опрос, если наступил его срок.
4. Перед отправкой каждого диагностического запроса повторно проверяется срок
   основного опроса. Если он наступил, сначала отправляется основной запрос.
5. Основной планировщик не сдвигает свои таймеры и не учитывает наличие
   диагностического режима.

### Отправка диагностических запросов

- Диагностический опрос активен только пока `/obd` запрашивает данные
- Все PID по умолчанию выключены и включаются галочками на странице
- Отправлять не более одного выбранного PID в секунду
- Отправка не должна блокироваться в `twai_transmit`
- Если очередь TWAI временно заполнена, повторить тот же PID без ожидания
- Не отправлять уже успешно поставленный в очередь запрос повторно

### Определение поддерживаемых PID

После открытия страницы `/obd` запросить маски поддержки:

- Mode 01 PID `00` для диапазона `01–20`
- PID `20`, `40`, `60` и последующие диапазоны только при наличии признака
  поддержки следующего диапазона
- Не предлагать для выбора PID, не отмеченные в масках автомобиля
- Сохранять обнаруженный набор до перезапуска устройства

### Общая база метрик

Вместо отдельных хранилищ для UDS и OBD-II использовать общую базу метрик:

- одна запись на физический параметр, а не на протокол или номер PID/DID
- значение, единица измерения, время обновления, признак валидности и источник
- UDS DID и OBD-II PID одного параметра обновляют одну и ту же запись
- последнее успешно декодированное значение становится текущим независимо
  от источника
- источник последнего обновления сохраняется для диагностики
- существующие дисплей, алерты и веб-интерфейс читают данные из общей базы

Примеры общих записей:

| Метрика | Infiniti DID | OBD-II PID |
|---------|--------------|-------------|
| Обороты двигателя | ECM `1201` | Mode 01 `0C` |
| Температура ОЖ двигателя | ECM `1101` | Mode 01 `05` |
| Напряжение бортовой сети | ECM `1103` | Mode 01 `42` |
| Температура масла двигателя | ECM `111F` | Mode 01 `5C`, если поддерживается |

Температура CVT, температура ОЖ радиатора, сигнал датчика давления масла и
сигнал датчика наддува остаются фирменными метриками, пока не найден достоверный
стандартный или фирменный аналог в физических единицах.

### Первый набор для витрины

После проверки масок добавить декодирование наиболее полезных поддерживаемых
PID:

- `04` — расчетная нагрузка двигателя
- `06`, `07` — топливные коррекции Bank 1
- `0A` — давление топлива
- `0B` — абсолютное давление во впуске
- `0D` — скорость автомобиля
- `0E` — угол опережения зажигания
- `0F` — температура воздуха на впуске
- `10` — массовый расход воздуха
- `11` — положение дросселя
- `1F` — время работы двигателя
- `23` — давление в топливной рампе
- поддерживаемые широкополосные A/F PID
- `2F` — уровень топлива
- `33` — атмосферное давление
- поддерживаемые температуры катализатора Bank 1
- `43` — абсолютная нагрузка
- `44` — заданное соотношение смеси
- `46` — температура окружающего воздуха
- поддерживаемые положения педали газа и дросселя
- `5E` — расход топлива, если поддерживается
- `61–64` — расчетные значения момента, если поддерживаются

### Ограничения

- Не отправлять управляющие запросы и команды исполнительных механизмов
- Не использовать Mode 04 и другие команды очистки диагностических данных
- Не перебирать фирменные DID полным диапазоном
- Не добавлять Bank 2, дизельные, гибридные и другие неприменимые PID
- Не изменять частоту существующего UDS-опроса

### Критерии готовности

- Период основного опроса остается равным
  `poll_interval_ms * количество основных DID`
- Фоновый сбор не содержит блокирующих ожиданий и искусственных пауз
- При совпадении срока первым отправляется основной UDS-запрос
- Неподдерживаемые и не выбранные PID не опрашиваются
- Общие UDS/OBD-метрики видны дисплею, алертам и веб-интерфейсу как одна метрика
- Потеря ответов фонового опроса не обнуляет данные основного опроса
- Есть нативные тесты масок поддержки, декодирования, приоритетов планировщика
  и совместного обновления метрик
- Все существующие нативные тесты продолжают проходить
